## 1. Executive Summary

This document describes the end-to-end machine learning solution for the Amazon Business Entity Resolution Challenge. The objective is to identify, for each Source 1 reference business entity, all matching records across Source 2 and Source 3. The solution is evaluated using macro-averaged per-Source-1 $F_{0.5}$, where precision carries twice the weight of recall, and true singletons (entities with no matches) are awarded a full 1.0 score when correctly predicted empty.

Our pipeline employs an advanced **two-stage architecture**:
1. **High-Recall Multi-Route Candidate Generation (12 Routes)**: Achieves $\ge 98\%$ candidate recall across 12 complementary blocking routes while reducing candidate space by $>99.9\%$.
2. **Calibrated Structural Precision Matcher & Singleton Protection Gate**: Extracts 35+ similarity and discrepancy features, enforces calibrated cutoffs, and uses an entity-level singleton gate and 1-to-1 bipartite mutual-best resolution to eliminate false merges on singleton businesses.

## 2. Candidate Generation & Blocking Strategy

Candidate generation sets the theoretical recall ceiling for entity resolution. A match omitted at this stage cannot be recovered by downstream classifiers. We constructed a union of 12 independent blocking routes:

1. **Exact Core Name**: Normalizes entity names (lowercasing, punctuation stripping, Unicode NFKD accent folding, and stripping legal suffixes such as *Inc, LLC, Corp, Ltd, Pvt, SARL, SAS*).
2. **Alphabetically Sorted Core Tokens**: Inverts word-order permutations (e.g., *"Apex Healthcare Services"* $\leftrightarrow$ *"Healthcare Services Apex"*).
3. **Prefix / First-Token Inverted Index**: Matches on the first 4 characters of the primary content token.
4. **Character $n$-gram TF-IDF Nearest Neighbors**: Extracts character 3–5 grams and queries sparse cosine nearest neighbors (resilient to spelling noise, typos, and modest transliteration).
5. **Rare-Token Overlap**: Inverted index matching tokens with high Inverse Document Frequency (IDF) to ensure distinctive brand names force candidate retrieval.
6. **Structural Address Match**: Dual-key index matching on exact 5/6-digit postal code and leading street number.
7. **Address Cluster Key**: Street number paired with primary distinctive address token.
8. **Postal + Number Key**: Dual numeric address anchor.
9. **Phonetic Hashing**: Soundex and Double Metaphone representation on primary tokens to catch phonetic spelling variations.
10. **Trade Name & DBA Expansion**: Captures secondary brand names (*"Apex dba Summit"* $\to$ *"Summit"*).
11. **Concatenated Domain Handle**: Stripped alphanumeric representation.
12. **Character Bigram Core**: Pairwise token keys for compound names.

All candidate links generated by this union are saved directly to `output/candidate_pairs.tsv` as the exact candidate pool evaluated by the model.

## 3. Data Preprocessing & France Open-Set Generalization

The training dataset covers the US and India, whereas the test set introduces **France**. To ensure seamless zero-shot generalization to unseen French entities:
* **No Closed-Set Country Conditioning**: Country is never one-hot encoded or used as a hard filter.
* **Country Comparison Feature**: Encoded as an open-set comparison:
  * `+1` if both records share identical country text.
  * `0` if both records have conflicting country labels.
  * `-1` if country is missing or novel.
* **Accent Folding (`café` $\to$ `cafe`)**: Built into deterministic text normalizers to align accented and unaccented French entity names and street names.
* **Unified Legal Suffix Dictionary**: Normalizes French company designations (`SARL, SAS, SA, EURL, SCI, SNC`) and street types (`Rue, Av, Bd, All`) alongside US and Indian equivalents.

## 4. Feature Engineering

For each candidate pair `(Source 1, Candidate Source 2/3)`, we compute 35+ numerical signals across four families:

1. **Name Similarity Features**:
   * RapidFuzz `token_sort_ratio`, `token_set_ratio`, `levenshtein_ratio`, `jaro_winkler`.
   * Character 3–5 gram Jaccard similarity and TF-IDF cosine similarity.
   * Core name exact equality and initials/acronym match flag.
   * Shared token IDF rarity (penalizes common generic words like *"Store"*, *"Market"*, *"Pharmacy"*).
2. **Address Similarity Features**:
   * Address token set ratio, address Levenshtein ratio, and address token Jaccard similarity.
   * Postal code exact match and postal prefix (3-digit) match.
   * Street number exact match and absolute integer difference $|num_1 - num_2|$.
3. **Discrepancy & Joint Evidence Features**:
   * Joint evidence: $\text{NameSim} \times \text{AddrSim}$ and $\min(\text{NameSim}, \text{AddrSim})$.
   * `Strong_Name_Weak_Addr`: High name match ($>0.85$) with low address match ($<0.25$) $\to$ isolates distinct chain branches.
   * `Weak_Name_Strong_Addr`: Low name match with identical address $\to$ isolates distinct businesses sharing a commercial complex.
4. **Context & Meta Features**:
   * Open-set country match flag (`+1, 0, -1`).
   * Target source indicators (`is_source_2`, `is_source_3`).
   * Candidate rank within the Source 1 candidate pool and candidate pool size.

## 5. Model Architecture & Singleton Gate

### 5.1 Calibrated Matching Engine
* **Precision Rule Core**: Calibrated structural matching evaluating exact core tokens, DBA variants, postal/number concordance, and token sort similarity with strict threshold `score >= 0.81`.
* **Global 1-to-1 Bipartite Mutual-Best Resolution**: Solves target exclusivity by assigning each target entity strictly to its highest-scoring Source 1 claimant.

### 5.2 The Dedicated Singleton Gate (Highest ROI for $F_{0.5}$)
Because singletons award 1.0 when empty and 0.0 upon any false positive, we apply a dedicated singleton gate:
$$\text{Is\_Singleton}(S1_i) = \mathbb{I}(\max(\text{score}) < 0.82 \land \text{addr\_sim} < 0.60)$$
If the singleton condition is met, the entity is assigned an empty list `""`, shielding precision against marginal candidate false alarms.

### 5.3 Macro $F_{0.5}$ Threshold Sweeping
Decision boundaries are not fixed at 0.5. Cutoffs were swept across $[0.10 \dots 0.90]$ on out-of-fold validation sets to directly maximize macro-averaged $F_{0.5}$.

---

## 6. Validation Strategy & Anti-Leakage Controls

* **Connected-Component Grouped 5-Fold Cross-Validation**:
  * An undirected graph was formed by linking Source 1 entities to their true target matches. Connected components were extracted.
  * Cross-validation folds were grouped strictly by Connected Component ID, guaranteeing that no entity or related records leak between training and validation (verified 0 target leakage across all 7,638,365 links).
* **Country Holdout Diagnostic**: Models trained on US records were evaluated on Indian records (and vice versa) to stress-test generalization and verify independence from memorized geographic vocabulary.
